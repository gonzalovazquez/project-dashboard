How to run these

Set it and forget it

  • Paste a week's prompt into a fresh Claude Code session opened on the Project Dashboard repo — one prompt starts one phase.
  • Each prompt is written to make its own routine implementation calls and only stop for genuine blockers, so an elevated permission mode (accept-edits or auto-approve) is what makes these actually unattended rather than a stream of confirmation prompts.
  • Work through the weeks in order — each prompt assumes the previous phase's scaffolding already exists in the repo.
Exception: Week 1 (Phase Three). It changes the schema of and writes to your live Brainstorming database, so its prompt stops at a dry-run diff for you to approve. Don't override that with auto-approve; this is the one phase worth watching.

If a phase is going to run unattended for hours or across a day, pair the kickoff prompt with /loop for a periodic heartbeat instead of checking in manually:

/loop 45m "Check progress on the current Project Dashboard phase task. If blocked, note why and continue with the next unblocked piece. If done, summarize and stop."

Send the phase's kickoff prompt first to start the real work — /loop only keeps nudging it forward, it isn't a substitute for the task itself.

Phase Three · Notion client and database setup

Goal: Connect the dashboard to the real Brainstorming database in Notion so it can read project status and write focus, next action and lifecycle back.

Review before merge: this phase changes the schema of and writes to your live Brainstorming database. Look at the dry-run schema diff before anything is applied.
Kickoff prompt 
Goal: Connect the dashboard to the real Brainstorming database in Notion so it can read project status and write focus, next action and lifecycle back. This is the foundation every later screen reads from.

Context: Repo: gonzalovazquez/project-dashboard (TypeScript, ESM, Node). Before anything else read README.md, docs/notion-schema.md and src/shared/types.ts. Existing code: the folder scanner in src/main/scanner (git history, GitHub link, tech, complexity, pulse), the focus rules in src/main/focus/rules.ts (progress, forecast, stall flags, health, closest-to-done ranking, and the limit of 3 focus projects), and Notion matching and parsing in src/main/notion. Run npm test and npm run typecheck before and after your changes; both must pass. The target interface is the interactive mockup in docs/ui-mockup.html (a macOS style window with a sidebar, an Overview screen and a per-project deep dive).
Notion is the source of truth for stage, ship criteria, next action, focus and lifecycle. The Brainstorming database already has Idea (title), Status (Not started, In progress, Beta, General Available), Category, Type and Priority. It does not yet have the properties the app needs. docs/notion-schema.md lists them: Focus (checkbox), Lifecycle (select: Active, Parked, Killed), Next action (text), Stage changed (date), Park reason (text) and Revisit on (date). Ship criteria are to-do blocks in the page body, with an optional hour estimate in brackets at the end of the text. The database's data source id is 308975d3-26ba-809d-92ce-000bc4085b1d. Writing to Notion from the first release was a deliberate decision: do not fall back to a local file for focus or next actions. Parsing already exists in src/main/notion/parse.ts and folder matching in src/main/notion/match.ts.

Approach:
1. Add the official Notion SDK (@notionhq/client). Check its current documentation for how databases and data sources are queried and which API version applies, rather than assuming.
2. Create src/main/notion/gateway.ts with a NotionGateway interface and a real implementation: list every page in the database (follow pagination), read a page's block children (follow pagination), update page properties (Focus, Lifecycle, Next action, Stage changed, Park reason, Revisit on), check or uncheck a to-do block, and create a page. Read the token from the NOTION_TOKEN environment variable for now; the keychain comes in the next phase.
3. Add a schema setup command, npm run notion:setup, that compares the live database with the properties above and prints what is missing. It must be a dry run by default and only change anything when run with --apply.
4. Stage changed: Notion does not record when a status changed. Implement a pure function detectStageChanges(previous, current) that returns the pages whose status differs from a stored snapshot, so the app can stamp Stage changed with today's date. Decide where the snapshot is stored (a JSON file under the app data folder is the starting assumption) and note the choice.
5. Add npm run notion:pull, a read-only command that fetches the board, runs matchFolders against the folders in a given directory, and prints which folders matched which pages and which did not.
6. Cover the gateway with unit tests using a fake client: pagination, property updates, block check and uncheck, and stage change detection.

Work autonomously: make routine choices yourself (file names, error types, retry handling) and iterate until npm test and npm run typecheck pass. If NOTION_TOKEN is set, run npm run notion:pull against the real board as a read-only check and use the output to adjust matching. Never run notion:setup with --apply and never write to the real database. Stop and wait for review before considering this phase done: this phase changes the schema of and writes to the live Brainstorming database, so present the dry-run schema diff and wait for approval to apply it.

When done: report the Notion API version you used, how Stage changed detection works and where the snapshot lives, the dry-run diff, which folders matched and which still need overrides, and any deviation from this plan.

Kickoff prompt 
Goal: Wrap the engine in an Electron app that scans on launch, merges Notion data, caches results, and exposes everything to the interface over a narrow, typed IPC surface. Every UI phase depends on the shape you choose here.

Context: Repo: gonzalovazquez/project-dashboard (TypeScript, ESM, Node). Before anything else read README.md, docs/notion-schema.md and src/shared/types.ts. Existing code: the folder scanner in src/main/scanner (git history, GitHub link, tech, complexity, pulse), the focus rules in src/main/focus/rules.ts (progress, forecast, stall flags, health, closest-to-done ranking, and the limit of 3 focus projects), and Notion matching and parsing in src/main/notion. Run npm test and npm run typecheck before and after your changes; both must pass. The target interface is the interactive mockup in docs/ui-mockup.html (a macOS style window with a sidebar, an Overview screen and a per-project deep dive). The Notion gateway from the previous phase lives in src/main/notion/gateway.ts and reads NOTION_TOKEN from the environment. The scanner can stream each project as it finishes (the onProject callback in scanRoot). Decisions already made: Electron for the shell, React with TypeScript and Vite for the interface, and a JSON cache in the app data folder (SQLite only if the cache proves too slow). The app must never modify the Development folder. The Notion token must be stored with Electron safeStorage, not in a plain file.

Approach:
1. Open choice: how to build Electron with Vite (for example electron-vite, vite-plugin-electron, or a hand-rolled setup). Evaluate two or three, pick one, and note the tradeoff.
2. Main process: a service that scans the configured Development folder (default ~/Development), pulls the Notion database, matches folders to pages, merges them into Project objects from src/shared/types.ts, writes the JSON cache, and emits an update as each folder finishes so the interface can fill in progressively.
3. Settings: the Development folder path and the Notion token, with the token encrypted via safeStorage. Include folder-to-page overrides as a settings field for now.
4. A typed preload bridge using contextBridge. Expose only: getSnapshot, startScan, onProjectUpdate, setNextAction, setCriterion, promote, park, kill, unpark, and settings read and write. Each mutating call runs the pure rules in src/main/focus/rules.ts first and then writes through the Notion gateway; a rejected rule (for example a fourth focus project) returns a typed error and writes nothing.
5. Renderer: a minimal React shell that lists projects from the snapshot. It exists only to prove the wiring; the real screens come next.
6. Security: contextIsolation on, nodeIntegration off, no remote content, and a restrictive content security policy.
7. Tests: unit-test the service and the IPC handlers with fakes for the filesystem, the scanner and the Notion gateway.

Work autonomously: choose names, structure and dependencies yourself. Iterate until npm test and npm run typecheck pass and the Electron app builds. If this environment cannot launch Electron, say so plainly and verify the main process logic through unit tests instead of claiming the window works. Flag me only if a required choice has no safe default, for example if safeStorage is unavailable on the target platform.

When done: report which build tooling you chose and why, the exact IPC surface, how the cache and settings are stored, whether you were able to launch the app, and any deviation from this plan.
